Every claim points to a results file in evals/results/ or a commit. Studies that were not run, or whose run was invalid, are reported as such and carry no number.

1. Problem and constraints

A freelancer spends hours reading job posts, deciding which ones are worth paid bids ("Connects") and writing proposals that prove they can do the work. GigBid automates the reading, filtering, evidence-finding and drafting. It never automates sending. A proposal, a client message or any spending of Connects stops at a LangGraph interrupt() and waits for the human. The marketplace receives only drafts the user approved, and every write carries an idempotency key, so a retry cannot submit twice.

Must never be automated: submitting a proposal, sending a message, spending Connects, accepting an offer, moving contact or payment off the platform, or claiming experience the portfolio does not support.

Constraints I actually worked under. They shape every result below. (i) Hosted open-weight models on Groq's free tier: 8,000 tokens per minute and 1,000 requests per day per model, read from Groq's own rate-limit headers. One drafted proposal costs about 29k tokens, so a single proposal needs several minutes of one model's quota, and every LLM study had to run on a small sample. (ii) Two models named in my config (llama-3.1-8b-instant, qwen3-32b) had been retired by Groq; I replaced them with qwen/qwen3.8-27b after checking the live model list (commit 0b65b2b). (iii) No starter kit: GigSim, the personas and the dev set are mine and synthetic (docs/DATA_CARD.md). (iv) No paid hosting: the public link runs on a free 512 MB host, which forced the lite deployment in §4.

2. Architecture

Bid graph (agent/graphs/bid_graph.py, rendered in docs/images/bid_graph.mmd): intake → Job Analyst ∥ Risk Assessor ∥ Fit Matcher (fan-out with Send, reducers merge their outputs) → decide → pricing → writer → claim verifier → critic (a weak draft returns to the writer at most twice) → compliance → dry-run preview → interrupt() approval → submit. Conversation graph (docs/images/conversation_graph.mmd): intent → liaison drafts a reply → compliance → approval → send.

Why each agent exists. Analyst: turns free text into a JobSpec (deliverables, skills, budget, screening questions, hidden needs). Risk Assessor: scams, planted injections and red flags, kept separate so a persuasive job cannot talk the writer out of a risk flag. Fit Matcher: the requirement-to-evidence matrix. Pricing: a quote from market statistics, client spend and the user's floor. Writer: the only free-text author. Verifier and Critic: grounding and quality. Compliance Guard: the marketplace rules in data/policy_pack/. Agents hand off Pydantic objects (agent/handoffs.py), not free text.

Marketplace port. All marketplace access goes through one interface (agent/marketplace_port.py) with two adapters, GigSim and live Upwork MCP (OAuth 2.1), switched by config. MCP surface: our own Portfolio (read), Marketplace (read + idempotent writes) and Workspace servers, plus the official GitHub MCP server for repo ingestion (docs/TOOLS.md). Each agent sees only an allowlist of tools. Stores: the Postgres checkpointer holds short-term thread state and survives restarts. A LangGraph store holds long-term memory written only by explicit rules: style memory learned from the user's edits, and outcome memory of what won or got replies per category. Raw tool output never goes into memory. The portfolio index lives in pgvector.

Two deployments. docker compose up runs the full system: separate MCP processes, the Arq worker and V8 retrieval. The public link runs on a free 512 MB host in "lite" mode: BM25 retrieval, with the worker and MCP servers in-process. Its cost in quality is measured in §4 rather than hidden.

3. R&D question A: tool granularity

Hypothesis. Many fine-grained tools with rewritten descriptions ("what to use it for, what not to use it for, an example") select the right tool more often than the published fine-grained descriptions, and far more often than 3 coarse "action + params" tools, at a higher token cost per task.

Setup. 40 tasks with a known correct call (evals/datasets/tool_tasks.jsonl), three tool sets (fine: 14 tools; coarse: 3; best: fine with rewritten descriptions), one forced tool call per task, scored on tool selection, argument accuracy and tokens (evals/runners/tool_study.py).

Source: evals/results/tool_study.json. Model qwen/qwen3.8-27b (GIGBID_PROFILE=open_alt, its own rate-limit bucket), first 15 of the 40 tasks (--limit 15). No call was rate-limited in this run. Malformed tool calls from the model count as wrong.

Reading. Coarse tools cost about a third of the prompt tokens but lose badly. Selection drops by a third (0.93 → 0.60) and argument accuracy halves, because the model must also pick the right action string and nest its arguments in params. That part of the hypothesis holds. The rewritten descriptions did not help on this model: they were worse than the published ones (0.80 vs 0.93) at slightly more tokens, so that part is refuted. With 15 tasks, one task is 6.7 points, so the fine-vs-best gap is two tasks. I cannot separate it from noise on a single run. Conclusion: keep fine-grained tools with their published descriptions. The description rewrite was not adopted.

An invalid run, discarded. The first run was invalid. Groq rate-limited 230 of its calls, and the runner scored each failed call as a wrong choice. I discarded that file rather than report it, fixed the runner (wait out 429s, exclude rate-limited calls and count them), and reran it. The table above is the valid rerun.

Hypothesis H5 not confirmed. On jobs with 4+ requirements, the shipped pipeline gains +7.1 points, about half of the 15 points hypothesised. Decomposition alone (V1) was worse than V0 overall (0.320 vs 0.346), so splitting a job into requirements did not by itself find better evidence. The gains come from hybrid retrieval (V2: +3.1 points) and above all from outcome-aware ranking (V4: +4.5 points over V3). Reranking alone (V3) bought nothing on recall (0.373 vs V2's 0.377) and added about 6 s at p50. The full-stack persona gains least (+2.0): its V0 baseline is already the highest. A plausible reason, not tested here, is that its case studies use the same technology words as job posts, which dense retrieval already matches.

What ships, and why. V8 corrective has the best recall, MRR and nDCG and a lower p95 than V4 (12.8 s vs 21.3 s). The reranker is the latency cost; it stays because V4/V8's outcome-aware gains are built on the reranked list. The public free-host link instead runs lite_bm25, because the models do not fit in 512 MB. On the same queries that costs 4.5 Recall@5 points and 5.9 nDCG points against V8, while still beating V0.

Claim verification. Every draft is split into claims, and each is graded supported, partly supported or unsupported against retrieved evidence (rag/verify.py). Unsupported claims are removed and partly supported ones rewritten before the Critic sees the draft. In the decision eval, the 4 drafted proposals averaged 3.5 claims each. There were 0.25 unsupported claims per proposal before verification and 0.00 after (decision_eval.json → unsupported_claims_per_proposal_before/after). n=4 proposals, so this shows the mechanism works; it does not estimate a rate.

Not completed: the one-component-at-a-time ablation (evals/runners/ablation.py is written but was not run within the free-tier budget) and the LLM-judge calibration. That calibration needs 30 items labelled by me, so no kappa is reported. I would rather report no number than an unlabelled one.

5. R&D question C: single agent vs supervisor vs graph

The comparison runner (evals/runners/compare_arch.py) runs the same jobs through (a) one ReAct agent with every read tool, (b) a prebuilt langgraph-supervisor with a research agent and a writer agent, and (c) the hand-built graph. It measures bid-or-skip accuracy, unsupported claims, compliance violations left in the final text, GigSim reply rate, tokens and latency.

Not measured by the deadline. At about 13–29k tokens per job and 8k tokens per minute per model, 50 jobs × 3 systems did not fit the free-tier budget alongside the decision eval, so there is no comparison table. The expected trade-off is that the graph spends fewer tokens because the parallel analysts use the small model, while a ReAct agent may do as well on simple single-skill jobs. That is a hypothesis, not a result.

7. Signature extension: proposal-strategy A/B test (X2)

Built: a second writer strategy, B (question-first and short, agent/prompts/writer_b.md), selected by proposal.strategy, and a paired A/B runner (evals/runners/ab_test.py). Each bid-worthy job is drafted with both strategies and submitted from two GigSim accounts, so the same simulated client judges both. The runner applies McNemar's exact test on discordant pairs and reports the minimum detectable effect. Not run within the budget, so no effect is claimed.

9. Safety and platform respect

Never: send without approval, contact or pay off-platform, fabricate experience, guarantee outcomes, follow instructions found inside job posts or client messages, or scrape. Enforcement, in layers: (1) untrusted text is wrapped in delimiters, and every prompt carries a preamble saying it is data, not instructions (agent/prompts/_untrusted.md); (2) the Risk Assessor flags injection patterns; (3) claim verification removes unsupported claims; (4) Compliance Guard checks the policy pack and banned phrases on the draft and on user edits; (5) interrupt() before every write, with idempotency keys on the marketplace port. What still gets through: the injection attack-success rate before and after defences is measured by evals/runners/injection_eval.py on the planted-injection dev jobs. The run was paused to give the decision eval the token budget, so it is reported only if evals/results/injection_eval.json is in the final commit. On the lite link, the verifier treats a claim as unsupported if the LLM grader is unavailable, so a grader outage removes claims rather than letting unchecked ones through.
